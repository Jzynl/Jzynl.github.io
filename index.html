Serengeti Suites

A hotel operations system: public booking site plus the staff dashboard that runs the day. The hotel originally asked for a booking website. What it needed was somewhere for three shifts of staff to see the same information: who is in which room, who has paid, what housekeeping has and hasn't done, and what today's money looks like.

The dashboard opens on occupancy, today's bookings and revenue, and outstanding balances. Every free room is a chip that opens a prefilled booking form. Housekeeping replaced its printed checklist with a per-room inspection and a readiness board that records who did what. Finance covers payments, expenses, refunds, budgets and a profit-and-loss view. The same codebase runs a working hotel in Zanzibar; Serengeti Suites is a second instance on sample data so the whole thing can be opened without exposing anyone's guests.

New features start as WhatsApp messages from reception and ship as small, targeted changes to the live system.

Case study: the hotel system behind Serengeti Suites
Problem

The hotel asked for a booking website. In practice it was running on paper and memory across three shifts: guest requests got lost between staff, housekeeping worked from a printed checklist, and nobody could see the day's figures without asking someone.

My contribution

Everything from the data model to the Nginx config: the public booking site, the staff dashboard, deployment and the ongoing changes.

Approach

Start from what reception does first thing in the morning and put that on one screen. Add features in the order staff ask for them, over WhatsApp, and ship each one as a small change to the live system rather than batching a release. Everything has to work on a phone, because that is what staff are holding.

Implementation
  • Dashboard home: occupancy, today's bookings and revenue, outstanding balances, free rooms as tappable chips that open a prefilled booking form
  • Bookings with source and channel tracking and per-channel commission rates
  • Room changes guarded against occupancy and maintenance conflicts; extend or change stay
  • Housekeeping: the paper checklist as a per-room digital inspection, a readiness board, and a history of who did what
  • ID photo capture at check-in with automatic image compression
  • Finance: payments, expenses, refunds, budgets and a profit-and-loss page with trends and CSV export
  • PostgreSQL, Gunicorn behind Nginx, nightly database backups
Outcome

In daily use by the staff of a working hotel. Serengeti Suites runs the same codebase on sample data and is the public demo linked above. I don't quote booking or revenue figures here because they belong to the hotel.

Case study: Hotel RAG
Problem

Guests ask reception the same questions at all hours. A chatbot that guesses is worse than none, so the assistant had to answer only from the hotel's own documents, hand off to reception when unsure, keep working if a component fails, and be measurable so changes can be judged.

My contribution

Architecture, implementation, deployment and evaluation.

Implementation
  • Hotel documents chunked and embedded into PostgreSQL with pgvector
  • Nginx in front of two stateless FastAPI replicas; questions go onto a Redis queue
  • Celery workers retrieve the nearest passages, optionally read the guest's live booking, and prompt the model to answer from that context only
  • Redis cache for repeat questions; booking answers are never cached
  • Every query logged with latency, token counts, and the prompt, model and document versions that produced it
  • A 20-question evaluation runs in CI and fails the deploy below a threshold
guest → Nginx → FastAPI ×2 → Redis queue → Celery ×2 → pgvector + hotel DB → LLM
                                 └ cache              └ query log
Status

Deployed and answering on the demo link above. Still being rolled out to the live hotel; evaluation results will be published here once the document set is final.

About

Natasha Lozzy

I'm a computer engineer and full-stack developer in Dar es Salaam, Tanzania.

What I'm curious about, in software and outside it, is how things are put together: which parts there are, how they depend on each other, why the thing behaves the way it does, and what changes when you move one piece. That's the same question whether I'm looking at a Django project's data model, the layout of a settings screen, a poster, or a building.

It's also why I end up working across the stack rather than in one layer. A booking form, the table it writes to, the report it feeds and the server it runs on are one system; a decision in any of them shows up in the others. I'd rather understand the whole shape than optimise one corner of it.

Usability is where that curiosity becomes a standard. Code that works and an interface that looks right are not the finish line; the finish line is a receptionist on a night shift, or a shop owner on a phone, getting what they came for without having to think about the software. Most of what I've learned has come from watching real people use what I built and adjusting.

I read and build beyond my formal field when something interests me, which lately means cloud infrastructure and the practical side of running AI models in production.

  1. Understand the structureWhat people actually do today, which parts are involved, and where it breaks.
  2. Design the interface for the taskClear hierarchy, one obvious next step, nothing that needs a manual.
  3. Build it as one systemInterface, application, data and deployment, decided together.
  4. Watch it in useShip, see what people do with it, and change it.
